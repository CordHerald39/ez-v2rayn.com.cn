## 修改一个端口会牵动哪些值
开发者界面文档给出一组相对关系：本地混合端口同时处理 SOCKS5 和 HTTP；第二监听端口为基础值加一，局域网端口加二，PAC 加三，Xray API 加四，mihomo API 加五，测试临时配置使用加二十一。端口关系不代表这些服务在任意模式下都会同时启动，但排查占用时只看基础值容易遗漏。

## 用日志确认是哪一个监听失败
先抄下当前基础端口，再查看启动错误是否明确给出端口号与地址。若日志只是远程连接超时，没有本地绑定失败信息，不应直接按端口冲突处理。对于错误涉及的端口，可以用 Windows 自带的只读命令查询监听者：
~~~powershell
Get-NetTCPConnection -State Listen -LocalPort 10808 |
  Select-Object LocalAddress, LocalPort, OwningProcess
~~~
10808 只是示例，执行时应替换成日志中的实际端口。结果为空只说明该次查询未发现 TCP 监听，不能排除 UDP 占用、瞬时冲突或权限问题。根据进程编号核对对应应用，避免凭印象结束未知系统进程。

## 调整之后一起对齐入口
若确认是你控制的另一份客户端占用，可先正常退出重复实例；确实需要同时运行时，再为各实例安排不重叠的端口范围。修改基础值后，检查派生值是否仍处于有效端口范围。
保存设置并重启相应服务后，核对浏览器、终端及手动配置应用填写的代理端口。它们可能仍指向旧值。此时“服务正常启动但应用打不开”可能是入口未同步，不能再次归咎于远程节点。

## 验收与恢复
验收应同时包含：日志不再出现绑定错误、预期端口由正确进程监听、指定应用能发出实际请求。仅看到界面启动不足以确认修复。如果改变后出现新问题，先恢复原端口和应用入口，再带两次日志继续定位。[首次代理配置](/articles/proxy-first-run/)说明了应用接入的基本步骤。
这些命令和检查点是排查建议，本站没有在你的 Windows 设备上执行。
